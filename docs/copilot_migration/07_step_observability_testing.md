# Шаг 6: Наблюдаемость и тестирование

## Цель
Подтвердить надежность миграции через метрики, логи и тесты до включения в основной поток.

## Что реализовать
1. Логировать для каждого запроса:
- provider
- model
- latency
- usage (если доступно)
- fallback reason (если был)
- policy decisions
2. Добавить smoke-тесты на типы запросов:
- classification
- calendar_event
- task
- note
3. Добавить негативные тесты policy режима.

## Правила
1. Логи должны быть машиночитаемыми (ключ-значение).
2. Ошибки должны содержать стабильные коды причин.
3. Тесты не должны требовать реального Telegram update при unit-уровне.

## Критерии успешности
1. Для каждого типа запроса есть успешный smoke.
2. Нет регрессий ключевого пользовательского флоу.
3. Негативные policy-тесты подтверждают text-only guardrails.

## Проверка
1. Запуск тестов и сбор отчета.
2. Ручной прогон нескольких запросов из README примеров.
3. Проверка логов на полноту telemetry.

## Риски
1. Скрытые регрессии в парсинге JSON от LLM.
2. Нехватка наблюдаемости при ошибках SDK.

## Решение рисков
1. Лог raw content до JSON parsing в debug-режиме.
2. Добавить correlation id запроса для трассировки.
