# Шаг 3: Переключение pipeline на LLM Gateway

## Цель
Перевести существующие обработчики (`request_handlers/*`) на новый `llm_core.gateway` без изменения бизнес-поведения.

## Что реализовать
1. Обновить `request_handlers/base_handler.py`:
- вместо `ModelRouter.generate(...)` использовать `LLMGateway.generate(...)`
2. Сопоставить текущие аргументы с `LLMRequest`.
3. Сохранить существующий формат промптов и парсинга.

## Правила
1. Не менять JSON-схемы ответов обработчиков (`calendar_event`, `task`, `note`).
2. Не менять текущую ветвящуюся бизнес-логику в `request_classifier.py`.
3. Любое изменение контракта возвращаемых объектов запрещено.

## Критерии успешности
1. Все типы запросов обрабатываются как и раньше.
2. Создание событий/задач/заметок не регрессирует.
3. В логах видно, что источник генерации теперь gateway/copilot.

## Проверка
1. Ручные запросы для каждого task type.
2. Проверка подтверждений в Telegram flow.
3. Сравнение результатов с базовой веткой до миграции.

## Риски
1. Скрытые зависимости от старого `ModelRouter`.
2. Изменение формата LLM-ответа.

## Решение рисков
1. Временный compatibility shim на период миграции.
2. Расширенное логирование raw response до парсинга.
